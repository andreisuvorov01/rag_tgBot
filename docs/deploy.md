## 1. Что уже есть в коде

Подключение внешнего OpenAI-совместимого API **уже реализовано** — отдельный
провайдер `openai_compatible` в `app/llm.py` (класс `OpenAICompatibleLLM`),
выбор через `LLM_PROVIDER` в `.env`. Локальная Ollama говорит по тому же
протоколу, поэтому «подключить реальный API» сводится к смене трёх значений
в `.env`.

| Возможность | Где |
|---|---|
| `POST {LLM_API_BASE}/chat/completions` с `Authorization: Bearer` | `app/llm.py` |
| `response_format: json_object`, авто-повтор без него, если провайдер не поддерживает | `_post_chat` |
| Автопереход на `max_completion_tokens`, если модель отвергает `max_tokens` | `_post_chat` |
| Повторы при 429/5xx и сетевых сбоях с учётом `Retry-After` | `LLM_RETRIES`, `_retry_after` |
| Отключение системного прокси для `localhost` (Windows) | `app/llm.py` |
| Провайдеры `openai_compatible` / `gigachat` / `anthropic` / `mock` | `make_llm` |
| **Учёт расхода токенов** (журнал + агрегат + `/usage`) | `app/usage.py` |
| **Двухуровневые модели**: дешёвая на классификацию/реранк/SQL | `LLM_MODEL_SMALL` |
| **Кэш ответов**: повторный вопрос не оплачивается дважды | `ANSWER_CACHE_SIZE` |
| Маскирование ПД во всех вызовах — и в чате, и в эмбеддингах | `AnonymizingLLM`, `EmbeddingService` |
| Деградация без падения: при ошибке API ответ собирается шаблоном из тех же данных | `app/qa.py` |
| Диагностика канала до API + пробные вызовы по шагам | `scripts/check_env.py --llm` |

## 2. Три схемы подключения

**Схема A — внешний API общего назначения** (OpenAI, DeepSeek, OpenRouter,
YandexGPT, Groq, Together). Меняются только `.env`. Плюс: ноль требований к
железу, качество модели не ограничено. Минус: промпты уходят за пределы сервера,
оплата по токенам.

**Схема B — свой GPU-сервер с OpenAI-совместимым движком** (vLLM, TGI,
Ollama, LM Studio). `LLM_API_BASE=http://<ваш-gpu-хост>:8000/v1`. Протокол тот
же, данные не покидают ваш контур, качество ограничено размером модели, который
влезает в видеопамять. Для 7B–14B в fp16/awq нужна карта от 16–24 ГБ.

**Схема C — гибрид** (рекомендуется и для чувствительных данных, и для экономии):
внешний API **только** для формулировки ответа, локально остаются эмбеддинги и
реранкер кросс-энкодером. Наружу уходят сжатые числовые payload'ы под
маскированием, а не целые документы; расход на токены падает в разы, потому что
самые объёмные операции (векторизация документов, переранжирование) выполняются
на CPU.

## 3. Конфигурация по провайдерам

Правило для всех: `LLM_API_BASE` — корень API **включая** `/v1`, клиент сам
дописывает `/chat/completions`. Ключ — в `LLM_API_KEY`.

### OpenAI

```env
LLM_PROVIDER=openai_compatible
LLM_API_BASE=https://api.openai.com/v1
LLM_API_KEY=sk-proj-...
LLM_MODEL=gpt-4.1               # основная модель: формулирует ответ
LLM_MODEL_SMALL=gpt-4.1-nano    # дешёвая: классификация, реранк, SQL
LLM_TEMPERATURE=0.2
LLM_MAX_TOKENS=1500
LLM_TIMEOUT_S=60
ANONYMIZE_PROMPTS=true
```

Новые модели линейки GPT-5 требуют `max_completion_tokens` вместо `max_tokens`
и часть из них не принимает нестандартную `temperature`. Клиент теперь
обрабатывает это сам: при 400 он повторяет запрос с правильным параметром
(`_post_chat`), поэтому такие модели тоже работают. Цены и актуальные имена
моделей сверяйте в [прайсе OpenAI](https://platform.openai.com/docs/pricing).

### DeepSeek (дешёвый и хорошо говорит по-русски)

```env
LLM_API_BASE=https://api.deepseek.com/v1
LLM_API_KEY=sk-...
LLM_MODEL=deepseek-flash                    # или deepseek-v4-pro (в 4,5 раза дороже)
LLM_THINKING=disabled                       # ОБЯЗАТЕЛЬНО, см. ниже
# LLM_MODEL_SMALL=deepseek-flash            # у DeepSeek обе роли закрывает одна модель
```

Совместим с OpenAI SDK; JSON-режим поддерживается. Домен `api.deepseek.com`
без `/v1` тоже работает — клиент дописывает путь сам.

> ⚠️ **Режим рассуждений включён по умолчанию.** DeepSeek по умолчанию генерирует
> цепочку рассуждений (`reasoning_content`) с усилием `high`. Эти токены
> **оплачиваются** (входят в `completion_tokens`) и **съедают `max_tokens`** — при
> жёстком лимите ответ приходит пустым: модель потратила весь бюджет на «мысли».
> В режиме рассуждений также игнорируется `temperature`. Поэтому
> `LLM_THINKING=disabled` — значение по умолчанию.
>
> **Что показал замер** (`python -m scripts.thinking_bench`, 3 прогона
> golden-набора на `deepseek-flash`, средние):
>
> | | disabled | low | high |
> |---|---|---|---|
> | ожидаемые числа в ответе | **6,7/7** | 6,0/7 | 6,0/7 |
> | верных и не оборванных | **6,7/7** | 5,0/7 | 6,0/7 |
> | токенов выхода | 2,3 тыс. | 3,3 тыс. | 3,0 тыс. |
> | из них «мысли» | 0 | 1,8 тыс. | 1,6 тыс. |
> | цена вопроса, ¥ | **0,0031** | 0,0046 (×1,5) | 0,0040 (×1,3) |
> | время ответа | **3,2 с** | 5,3 с | 5,2 с |
>
> Вывод: на задачах этого бота (разбор таблиц, пересчёт долей, короткий вывод по
> фрагментам) рассуждения **не улучшают ответы**, но стоят в 1,3–1,5 раза дороже
> и почти вдвое медленнее. Причина: абсолютные суммы, прогноз и отклонения считает
> код — модели остаётся пересказ, «думать» тут не о чем. Дополнительно включённые
> рассуждения **добавляют токены и во вход** (48 против 22 на одном и том же
> промпте), а «мысли» занимают ~91% выхода. Включайте осознанно:
> `LLM_THINKING=low|high|max`, при желании только для ответов —
> `LLM_THINKING_TASKS=compose`. Воспроизвести замер:
>
> ```bash
> python -m scripts.thinking_bench --for-compose --repeat 3
> ```

### OpenRouter (агрегатор: один ключ — сотни моделей)

```env
LLM_API_BASE=https://openrouter.ai/api/v1
LLM_API_KEY=sk-or-v1-...
LLM_MODEL=anthropic/claude-sonnet-4.5       # ответ
LLM_MODEL_SMALL=google/gemini-2.5-flash     # служебные шаги
```

Для атрибуции OpenRouter рекомендует заголовки `HTTP-Referer` и `X-Title`;
клиент отправляет только `Authorization`, и без этих заголовков запросы
обслуживаются штатно. Формат `response_format` поддерживают не все модели
каталога — на неподдерживающих сработает авто-повтор без него.

### YandexGPT (данные в РФ)

```env
LLM_API_BASE=https://llm.api.cloud.yandex.net/v1
LLM_API_KEY=<API-ключ сервисного аккаунта>
LLM_MODEL=gpt://<folder_id>/yandexgpt/latest
```

Обратите внимание: у YandexGPT имя модели содержит `gpt://<folder_id>/...` —
это указывается целиком в `LLM_MODEL`, отдельного поля для folder_id нет.

### Azure OpenAI (свой формат URL)

Azure не использует `/chat/completions` в корне: путь включает deployment и
`api-version`, а ключ идёт в заголовке `api-key`, не `Authorization`. Текущий
клиент к Azure **не подключится без доработки** — нужен либо
[OpenAI-совместимый шлюз перед Azure](https://learn.microsoft.com/azure/ai-services/openai/),
либо правка клиента. Самый простой обход — поставить перед Azure прокси-шлюз
(LiteLLM и подобные), который отдаёт стандартный `/v1`.

### Свой GPU-сервер (vLLM)

На GPU-машине:

```bash
docker run --gpus all -p 8000:8000 \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3-14B-Instruct-AWQ \
  --served-model-name qwen3-14b \
  --max-model-len 16384
```

В `.env` бота:

```env
LLM_PROVIDER=openai_compatible
LLM_API_BASE=http://<gpu-host>:8000/v1
LLM_API_KEY=EMPTY          # vLLM по умолчанию ключ не проверяет
LLM_MODEL=qwen3-14b
ANONYMIZE_PROMPTS=false    # данные не покидают ваш контур
```

Порт 8000 держите либо в приватной сети, либо за обратным прокси с
авторизацией: vLLM без ключа открыт всем, кто до него дотянется.

### Эмбеддинги через тот же API (опционально)

```env
EMBEDDINGS_PROVIDER=api
EMBEDDINGS_API_BASE=https://api.openai.com/v1
EMBEDDINGS_API_KEY=sk-proj-...
EMBEDDINGS_API_MODEL=text-embedding-3-small
EMBEDDINGS_DIM=1536        # ОБЯЗАТЕЛЬНО совпадает с размерностью модели
```

> ✅ **Маскирование.** Запросы к внешнему embeddings-endpoint проходят через ту
> же защиту, что и чат-вызовы: при `ANONYMIZE_PROMPTS=true` из текстов
> вычищаются ИНН, счета, телефоны, e-mail, паспорта и названия организаций
> (`app/embeddings.py`). При `false` фрагменты документов уходят сырыми —
> стартовая проверка в `app/main.py` об этом предупредит.
>
> 💰 **Экономика.** Векторизация — самая объёмная операция по тексту: каждый
> загруженный документ превращается в десятки фрагментов. Через внешний API это
> заметные деньги, локально — только время CPU. Поэтому для экономии
> `EMBEDDINGS_PROVIDER=sentence_transformers` (0,5 ГБ ОЗУ на `e5-small`).
>
> ⚙️ **Размерность.** При `EMBEDDINGS_PROVIDER=api` значение `EMBEDDINGS_DIM`
> должно совпадать с моделью: `text-embedding-3-small` → 1536,
> `text-embedding-3-large` → 3072. Смена модели меняет отпечаток векторов и
> требует переиндексации — система предупредит при старте.

После смены модели эмбеддингов обязательна переиндексация — векторы разных
моделей несовместимы:

```bash
python -m scripts.reindex
```

Система сама предупредит о несовпадении отпечатка при старте
(`check_embeddings_fingerprint` в `app/main.py`).

### Проверка конфигурации

```bash
python scripts/check_env.py        # ping LLM API + подсказки по экономии токенов
python scripts/check_env.py --llm  # пробные вызовы по шагам: JSON-режим и объём промптов
python -m scripts.e2e_live         # СКВОЗНОЙ прогон на живом API (демо-данные, golden-вопросы)
python -m scripts.eval_demo        # то же offline (mock LLM) — для регрессии без расходов
python -m scripts.llm_usage        # расход токенов и оценка в деньгах
```

`scripts/e2e_live.py` проверяет именно связку «провайдер → клиент → верификатор →
ответ»: загружает демо-отчёты (парсинг локальный, 0 токенов), задаёт golden-вопросы
через живой API и проверяет, что нужные числа есть в ответе, ответ не оборван
лимитом токенов, а повторный вопрос не стоит ни одного обращения к API. Показывает
фактическую цену вопроса по `LLM_PRICES`. Расход на прогон — около 3 ¥ центов
(замер: 19 вызовов, 14 тыс. токенов входа).

## 4. Экономия токенов

Платный во всей системе только внешний LLM API, и платят за **токены**. Ниже —
что уже реализовано и какие настройки дают экономию. Порядок — по убыванию
эффекта.

### 4.1. Дешёвая модель на служебные шаги (самый крупный эффект)

Ответ формулирует **одна** модель, а классификация, реранкинг и генерация SQL
вызываются на каждый вопрос чаще. Эти шаги отдаются дешёвой модели:

```env
LLM_MODEL=gpt-4.1               # формулирует ответ
LLM_MODEL_SMALL=gpt-4.1-nano    # классификация, реранкинг, SQL
LLM_MODEL_SMALL_TASKS=classify,rerank,sql
```

`compose` в этот список попасть не может — ответ всегда на основной модели,
даже если его там указать (есть тест). Если `LLM_MODEL_SMALL` пуст, работает
одна модель на всё — как раньше.

Почему это выгодно: классификация возвращает ~40 токенов JSON, реранкинг —
десяток оценок «0/1/2», SQL — один SELECT. Дорогая модель на этих шагах не
добавляет качества, только счёт. На дешёвой модели JSON просим словами, а не
через `response_format`: лишний 400 — это заново оплаченный промпт.

### 4.2. Не вызывать модель там, где код уже посчитал

```env
COMPOSE_MODE=auto         # шаблон для факта, сравнения, состава, прогноза, план/факт
CLASSIFY_WITH_LLM=false   # намерение определяют правила, бесплатно
RERANKER=crossencoder     # локальный кросс-энкодер вместо вызова модели
```

`auto` — компромисс по умолчанию: числа и таблицы система считает сама и уже
сверстала, модель вызывается только там, где она пишет текст («что говорится в
документах», причины, ранжирование). `COMPOSE_MODE=llm` заметно улучшает
формулировки, но платит за каждый вопрос — включайте осознанно.

Локальный кросс-энкодер вместо LLM-реранкера экономит самый большой промпт
(в него уходят фрагменты документов), но требует модель в ОЗУ.

### 4.3. Кэш ответов

```env
ANSWER_CACHE_SIZE=64
```

Повторный вопрос (тот же пользователь или коллега из той же организации)
отдаётся из памяти: **ноль вызовов и ноль токенов**. Кэшируются только ответы,
которые целиком состоят из текста модели; ответы, собранные кодом, и так
бесплатны, поэтому не кэшируются — так у них не теряются график и кнопки Excel.
Сброс — при перезапуске процесса.

### 4.4. Границы на объём промптов и ответов

```env
COMPOSER_MAX_TOKENS=200     # верхняя граница стоимости ответа
CLASSIFIER_MAX_TOKENS=120   # JSON-схема укладывается в 120
SQL_MAX_TOKENS=400
RERANK_MAX_TOKENS=600
RERANK_MAX_ITEMS=8          # сколько кандидатов уходит в реранкер
RERANK_SNIPPET_CHARS=200    # сколько символов фрагмента видит модель
COMPOSER_CONTEXT_ITEMS=5    # сколько фрагментов документов в промпте ответа
COMPOSER_CONTEXT_CHARS=200  # сколько символов каждого фрагмента
COMPOSER_HISTORY_ROWS=24    # сколько строк истории (ряды данных)
```

Блок `COMPOSER_CONTEXT_*` — самый крупный вклад во входной промпт: 5 фрагментов
× 200 символов ≈ 450 токенов входа на каждый вопрос «что говорится в
документах». Уменьшение даёт прямую экономию, но слишком сильное режет качество
вывода по документам — меняйте осознанно и проверяйте на `eval_demo`.

`COMPOSER_MAX_TOKENS` — это прямое ограничение сверху: сколько бы модель ни
«лила воды», больше этого числа токенов вы не оплатите.

### 4.5. Встроенный подсчёт расхода и контроль баланса

Каждый вызов API фиксируется провайдером в поле `usage`, и система его
сохраняет. Три способа посмотреть:

```bash
python -m scripts.llm_usage              # сводка: по моделям, задачам, деньги
python -m scripts.llm_usage --balance    # когда кончался баланс и сколько раз
python -m scripts.llm_usage --journal -n 50   # последние 50 вызовов построчно
python -m scripts.llm_usage --json       # машинночитаемый вид
```

В Telegram — команда `/usage`. Чтобы видеть деньги, задайте тарифы и баланс
(в одних и тех же деньгах):

```env
LLM_PRICES="deepseek-flash=1/4"    # ¥ за 1 млн токенов: вход/выход
LLM_BALANCE=33                     # баланс ключа: тогда /usage покажет остаток
```

Формат — «модель=вход/выход» за 1 млн токенов. Без цен отчёт покажет токены, но
не стоимость. Кэшированный префикс (`cached_tokens`) учитывается отдельной
строкой — у провайдеров он дешевле, а оценка по полной цене даёт верхнюю границу.

Журнал всех вызовов — `data/llm_usage.jsonl`, агрегат по моделям и задачам —
в таблице `app_meta` (переживает перезапуск). Пример вывода:

```
📊 Расход токенов LLM
Всего вызовов: 128
Вход: 118,4 · выход: 21,7 (тыс.)
Оценка стоимости: ¥0,0731

По моделям:
• deepseek-flash: 128 выз., 118,4→21,7 · ¥0,0731

По задачам:
• ответ: 96 выз., ...
• реранкинг: 32 выз., ...

💰 Баланс: 33 − израсходовано 0.0731 = осталось 32.9269
Средняя цена вопроса 0.00076; остатка хватит примерно на 43 000 вопросов с моделью.
```

### 4.6. Когда на ключе закончился баланс

Провайдер отвечает **HTTP 402** (DeepSeek: `402 Insufficient Balance`), у
OpenAI и шлюзов бывает `insufficient_quota` в 400/403/429. Система различает
«кончились деньги» и «сеть отвалилась» и ведёт себя так:

1. **повторов нет** — 429/5xx повторяются, 402 нет: деньги не появятся от
   ожидания, а каждый повтор оставляет ошибку в журнале провайдера;
2. **пауза** `LLM_BALANCE_RETRY_S` (по умолчанию 300 с): пока не истекла, в API
   не обращаемся вовсе — иначе каждый вопрос пользователя давал бы новую пачку
   ошибок. По истечении паузы система сама пробует снова, так что после
   пополнения счёта ничего перезапускать не нужно; `0` отключает паузу;
3. **ответ всё равно отдаётся** — шаблоном из тех же данных: цифры верные,
   теряются только формулировки модели;
4. **пользователь получает предупреждение** один раз на эпизод — «на ключе
   закончился баланс, пополните счёт». Предупреждение показывается только там,
   где ответ без модели теряет смысл (вывод по документам, ранжирование, SQL);
   в фактах и сравнениях, которые и так отвечаются шаблоном, его нет;
5. **событие фиксируется**: `data/llm_usage.jsonl` (запись с
   `event: balance_exhausted`) и счётчик в `app_meta`. Состояние хранится в
   клиенте, а не только в исключении: шаги вроде классификатора и Text-to-SQL
   перехватывают ошибку и продолжают работу, поэтому по одному пойманному
   исключению событие можно было бы потерять. Посмотреть, сколько запросов
   упало и когда это началось:

   ```bash
   python -m scripts.llm_usage --balance
   ```

6. в `/usage` появляется строка «Баланс API исчерпывался: N раз, последний —
   <дата>» и пометка, что API сейчас не опрашивается.

### 4.7. На сколько хватит баланса

```bash
python -m scripts.balance_forecast                    # DeepSeek flash, 33 ¥
python -m scripts.balance_forecast --model pro        # тариф pro
python -m scripts.balance_forecast --peak --cache-hit 0.2
python -m scripts.balance_forecast --price-input 2 --price-output 8
```

Скрипт считает двумя способами: **по факту** — берёт реальные токены на вопрос
из учёта, если API уже вызывался; **по модели расходов** — по структуре
промптов (см. [раздел 10](#10-сколько-это-стоит)). Готовые цифры для 33 ¥ — там же.

### 4.8. Локальные эмбеддинги — обязательны

```env
EMBEDDINGS_PROVIDER=sentence_transformers
EMBEDDINGS_LOCAL_MODEL=intfloat/multilingual-e5-small   # dim 384, ~0,5 ГБ ОЗУ
REQUIRE_LOCAL_EMBEDDINGS=true                            # значение по умолчанию
```

Векторизация — самая объёмная операция по тексту: каждый загруженный документ
превращается в десятки фрагментов, и через платный API это прямые деньги **за
каждую загрузку**, а не за вопрос. Локальная модель делает то же бесплатно.

Поэтому внешний embeddings-endpoint не «не рекомендуется», а **запрещён при
старте**: `app/main.py` отвергает конфигурацию, где `EMBEDDINGS_PROVIDER=api`
указывает не на localhost, и печатает объяснение с готовой строкой для
осознанного исключения (`REQUIRE_LOCAL_EMBEDDINGS=false`, тогда обязателен
`ANONYMIZE_PROMPTS=true` — маскирование для embeddings-API реализовано).

Не путайте с LLM API: генерация текста по токенам стоит копейки и вынесена
наружу, а векторизация — нет.

### 4.9. Чего не делать

- **Не уводите эмбеддинги во внешний API ради экономии**: векторизация —
  самая объёмная операция по тексту, локальная модель `e5-small` (0,5 ГБ ОЗУ)
  обходится бесплатно. По умолчанию такой запуск просто отвергается
  ([4.8](#48-локальные-эмбеддинги--обязательны)).
- **Не включайте `ANONYMIZE_PROMPTS=false`** на внешнем endpoint: маскирование
  не увеличивает расход, а экономия на нём — ложная.
- **Не поднимайте `ANSWER_RETRIES` без нужды**: каждый повтор верификатора —
  это ещё один оплаченный вызов композитора. `2` — разумный компромисс.
- **Не выбирайте reasoning-модели** для этого конвейера: они генерируют сотни
  «мыслящих» токенов на каждый шаг, а служебные шаги у нас — короткий JSON.
  При равном качестве берите нерассуждающую модель.

## 5. Грабли совместимости

| Грабли | Проявление | Что делать |
|---|---|---|
| `response_format` не поддерживается моделью | HTTP 400 на классификаторе и реранкере | Уже обработано: клиент повторяет запрос без `response_format` |
| Модель «льёт воду» вокруг JSON | `parse_json_block` не находит объект | Классификация/реранкер возвращают безопасный дефолт |
| Новые модели требуют `max_completion_tokens` | HTTP 400 → шаблонный ответ | Уже обработано: автопереход на `max_completion_tokens` |
| Провайдер не принимает `temperature != 1` | HTTP 400 | Уже обработано: повтор без `temperature` |
| Лимит `COMPOSER_MAX_TOKENS` слишком мал для «умной» модели | Обрыв ответа на полуслове | Поднять до 400–800: с внешним API ограничение по времени неактуально |
| Обрезка «умного» ответа верификатором | Модель добавляет вычисленные проценты, которых нет в данных | Для прогноза/состава/сравнения производные (разности, суммы, проценты) разрешены и считаются точно из данных; отключается `VERIFY_ALLOW_DERIVED=false` |
| Рейт-лимит 429 | Был бы шаблонный ответ на весь вопрос | Уже обработано: `LLM_RETRIES=3` + `Retry-After` |
| Системный прокси Windows перехватывает localhost | Зависание на локальной Ollama | Уже обработано (`trust_env=False` для локальных адресов) |
| Смена модели эмбеддингов без переиндексации | Семантический поиск молча деградирует | `python -m scripts.reindex` |
| Промпт-кэш провайдера не срабатывает | Полная цена за вход при повторах | Статический системный промпт идёт первым сообщением — так провайдер кэширует префикс; у DeepSeek/OpenAI это происходит автоматически при повторяющемся префиксе ≥1024 токенов |

## 6. Что даёт реальный API

### Качество

- **Реранкер.** Сейчас в `.env` стоит `RERANKER=heuristic`, потому что на модели
  1,5B LLM-оценка релевантности медленная и неточная. С внешним API ставится
  `RERANKER=llm` — это самый дешёвый прирост точности по практике Onyx/Anthropic
  (реранк после RRF). Маскирование фрагментов уже работает.
- **Классификатор.** `CLASSIFY_WITH_LLM=false` экономит ~18 секунд на CPU. С
  внешним API ставится `true` — лучше разбираются формулировки, которые правила
  не ловят (косвенные вопросы, многосоставные условия, «что если»).
- **Композитор.** `COMPOSE_MODE=auto` отдаёт шаблоном всё, что код уже посчитал.
  С внешней моделью есть смысл `COMPOSE_MODE=llm` — ответы перестают быть
  «телеграммами» и добавляют выводы. Именно здесь внешний API заметен
  пользователю сильнее всего.
- **Text-to-SQL.** Генерация запроса — самая требовательная к модели операция;
  на 1,5B она работает плохо. С внешним API «гибкие вопросы» начинают отвечать.
- **Vision-OCR.** `OCR_VLM_ENABLED=true` даёт распознавание сканов, которые не
  берёт Tesseract (см. предупреждение о приватности в `.env.example`).

### Скорость

Замеры проекта на CPU: классификация ~18 с, композитор ~0,9–1,5 с, вопрос
целиком 3–5 с, кнопка «Прогноз» до 37 с при двух вызовах. Внешний API снимает
зависимость от локального CPU: вместо десятков секунд — 1–3 с на вызов, и
появляется смысл в тех шагах, которые сейчас отключены ради экономии времени.
**Задержка начинает определяться сетью и очередью провайдера, а не вашим
железом.**

### Требования к серверу

Радикально падают. Локальная схема требует ~3 ГБ ОЗУ под модели (Ollama
1,5–2 ГБ + эмбеддинги 0,6 ГБ). С внешним API и локальными эмбеддингами
хватает **2 ГБ ОЗУ и 2 vCPU** — модель на сервере не живёт вовсе. Если и
эмбеддинги увести в API, для бота достаточно 1 ГБ.

### Чего это стоит

- Промпты (фрагменты документов, названия показателей) уходят на сторону
  клиента API. `ANONYMIZE_PROMPTS=true` маскирует ИНН, счета, телефоны, e-mail,
  паспорта и названия организаций, но не сам текст отчетов. Для финансовой
  отчётности это чаще всего неприемлемо без договора о конфиденциальности —
  отсюда схема C.
- Доступность ответа зависит от провайдера: при сбое API система отдаст
  шаблонный ответ (данные те же), но «живого» текста не будет.
- Расход по токенам, см. [раздел 10](#10-сколько-это-стоит).

## 7. Развёртывание без Docker (systemd)

Выбранный режим: **никаких контейнеров**. PostgreSQL устанавливается на хост,
бот работает как systemd-сервис. Это меньше движущихся частей, обновление —
`git pull` + `pip install` + `systemctl restart`, а логи идут в journald.

### 7.1. Требования

| Ресурс | Минимум (внешний API, локальные эмбеддинги) | Комфорт |
|---|---|---|
| ОЗУ | 2 ГБ | 4 ГБ |
| CPU | 2 vCPU | 2–4 vCPU |
| Диск | 20 ГБ SSD | 40 ГБ |
| ОС | Ubuntu 22.04/24.04 LTS, Debian 12 | — |

Ubuntu 24.04 несёт Python 3.12 в репозитории — это минимальная версия проекта.
На Ubuntu 22.04 (Python 3.10) нужен PPA `deadsnakes` либо готовый venv с 3.12.

Доступ к `api.telegram.org` — обязательное условие, поэтому российские VPS без
проксирования не подходят. Проверить одной командой на сервере:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' https://api.telegram.org
```

Если 200 — всё хорошо. Если таймаут — нужен `TELEGRAM_PROXY` (см.
[раздел 12](#12-диагностика-проблем)) либо хостинг вне зоны блокировки.

### 7.2. Подготовка сервера

```bash
# от root
adduser --disabled-password --gecos "" rag
usermod -aG sudo rag
apt update && apt upgrade -y
apt install -y git curl ufw unattended-upgrades

# SSH: ключи вместо пароля
# на локальной машине: ssh-copy-id rag@<ip сервера>
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl reload ssh

# файрвол: наружу только SSH (вебхук не используем — long polling)
ufw allow OpenSSH
ufw --force enable
```

### 7.3. PostgreSQL 16 + pgvector на хосте

```bash
# официальный репозиторий PostgreSQL (в репозитории Ubuntu версия старее)
apt install -y postgresql-common
/usr/share/postgresql-common/pgdg/apt.postgresql.org.sh -y
apt install -y postgresql-16 postgresql-16-pgvector

# база и пользователь. ВАЖНО: всё в одном сеансе psql — `\c rag` переключает
# базу только внутри него, а CREATE EXTENSION должен попасть именно в rag
sudo -u postgres psql <<'SQL'
CREATE USER rag WITH PASSWORD 'ЗАМЕНИТЕ_НА_СЛОЖНЫЙ_ПАРОЛЬ';
CREATE DATABASE rag OWNER rag;
\c rag
CREATE EXTENSION IF NOT EXISTS vector;
SQL

# слушать только localhost (по умолчанию так и есть — проверьте)
grep -E "^listen_addresses" /etc/postgresql/16/main/postgresql.conf
```

Проверьте, что расширение легло **в базу `rag`**, а не в `postgres` — иначе
таблицы с векторами не создадутся, и ошибка будет выглядеть как «таблица
`documents` не существует»:

```bash
sudo -u postgres psql -d rag -c "\dx vector"
sudo -u postgres psql -d rag -c "\dt"      # на чистой базе пусто — это нормально
```

Таблицы создаёт само приложение при первом запуске (`make_engine` вызывает
`create_all`), отдельная миграция не нужна. Появились они или нет — видно в
`scripts/check_env.py`: строка «Расширение pgvector» и «Таблицы в схеме public».

`pg_hba.conf`: строка для `rag` должна требовать пароль с `127.0.0.1/32`
(`scram-sha-256`). Наружу порт 5432 не открывайте — `ufw` его и так не пускает.

Отдельный пользователь только для чтения (рекомендация для Text-to-SQL):

```bash
sudo -u postgres psql -d rag <<'SQL'
CREATE USER rag_ro WITH PASSWORD 'ДРУГОЙ_ПАРОЛЬ';
GRANT CONNECT ON DATABASE rag TO rag_ro;
GRANT USAGE ON SCHEMA public TO rag_ro;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO rag_ro;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO rag_ro;
SQL
```

Кэш моделей — рядом с проектом, чтобы не забивать корневой раздел:

### 7.5. Конфигурация `.env`

Минимальная конфигурация для экономии токенов (полный разбор — [раздел 4](#4-экономия-токенов)):

```env
# --- Telegram ---
BOT_TOKEN=<токен от @BotFather>
ALLOWED_USER_IDS=<ваш telegram id>      # либо свой REG_CODE, но не дефолтный
REG_CODE=<случайная строка>
STRICT_STARTUP=true

# --- База на хосте ---

LLM_API_KEY=<ключ>

LLM_TIMEOUT_S=60

# --- Экономия токенов ---

# --- Эмбеддинги: локально (ноль токенов) ---

EMBEDDINGS_LOCAL_MODEL=intfloat/multilingual-e5-small

```

```bash
chmod 600 /var/www/TgRag/.env        # ключи API и токен бота — только владельцу
```

Проверка до запуска сервиса:

```bash
cd /var/www/TgRag
HF_HOME=/var/www/TgRag/hf-cache venv/bin/python scripts/check_env.py --llm
```

`--llm` делает пробные вызовы по шагам и показывает, какая модель на каком шаге

### 7.6. systemd-сервис

`/etc/systemd/system/rag-bot.service`:

```ini
[Unit]
Description=RAG financial assistant (Telegram bot)
After=network-online.target postgresql.service
Wants=network-online.target
Requires=postgresql.service

[Service]
Type=simple
User=rag
Group=rag
WorkingDirectory=/var/www/TgRag
EnvironmentFile=/var/www/TgRag/.env
Environment=HF_HOME=/var/www/TgRag/hf-cache
Environment=PYTHONUNBUFFERED=1
Environment=PYTHONIOENCODING=utf-8
# кэши временных файлов — рядом с проектом
Environment=TMPDIR=/var/www/TgRag/rag-tmp
ExecStart=/var/www/TgRag/venv/bin/python -m app.main
Restart=always
RestartSec=5
# при утечке памяти процесс перезапустится, а не утащит сервер в swap
MemoryMax=1500M
# минимальные права
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=full
ProtectHome=read-only
ReadWritePaths=/var/www/TgRag

[Install]
WantedBy=multi-user.target
```

`ProtectSystem=full` оставляет доступным на запись только то, что перечислено в
`ReadWritePaths`, — каталог приложения. `ProtectHome=read-only` при этом не
мешает: `/var/www/TgRag` лежит вне домашних каталогов. Каталоги `rag-tmp` и
`hf-cache` создайте заранее:

```bash
mkdir -p /var/www/TgRag/rag-tmp /var/www/TgRag/hf-cache
```

Журнал systemd ограничьте, иначе логи съедят диск. `/etc/systemd/journald.conf`:

```ini
SystemMaxUse=500M
```

Запуск:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now rag-bot
sudo systemctl status rag-bot
journalctl -u rag-bot -f
```

Ожидаемый вывод в логе:

```
=== Финансовый ассистент (RAG + LLM) ===
БД:           postgresql+asyncpg
LLM:          openai_compatible (deepseek-chat)
Эмбеддинги:   sentence_transformers
Реранкер:     crossencoder
Верификатор:  вкл
```

Автозапуск после перезагрузки — `enable`. Обновления ОС —
`unattended-upgrades` (`dpkg-reconfigure -plow unattended-upgrades`).

### 7.7. Если Docker всё-таки нужен

В репозитории остаётся `docker-compose.yml` (PostgreSQL 16 + pgvector + бот),
но учтите: `sentence-transformers` закомментирован в `requirements.txt`, поэтому
в образе локальных эмбеддингов не будет. Либо раскомментируйте зависимость и
пересоберите образ, либо в контейнере работайте без них
(`EMBEDDINGS_PROVIDER=hash` — качество поиска ниже, либо `api` — токены и
приватность). Для выбранного режима без Docker этот вариант не нужен.

### 7.8. Что разворачивается (архитектура)

```
Внешний LLM API ─────┐
                     │ (только промпты, маскированные при ANONYMIZE_PROMPTS=true;
Telegram API ────────┤  эмбеддинги и реранкер — локально)
                     ▼
              ┌──────────────┐
              │ бот (aiogram)│  long polling, исходящие соединения
              │ + QA-конвейер│  systemd: rag-bot.service
              └──────┬───────┘
                     ▼
              PostgreSQL 16 + pgvector на хосте
              127.0.0.1:5432, наружу закрыт (ufw)
                     │
              data/uploads, data/расходы.xlsx, data/llm_usage.jsonl
```

Никаких входящих портов, кроме SSH: бот работает на long polling, поэтому
домен, TLS-сертификат и обратный прокси не нужны. Это заметно упрощает
развёртывание и сокращает поверхность атаки.

### Бэкап

Бэкапить нужно два места: БД и каталог `data` (оригиналы документов,
Excel-журнал расходов, журнал расхода токенов).

```bash
mkdir -p /var/backups/tgrag

#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date +%F_%H%M)
# -Fc: сжатый формат, восстанавливается pg_restore
sudo -u postgres pg_dump -Fc rag > /var/backups/tgrag/rag-$STAMP.dump
tar czf /var/backups/tgrag/data-$STAMP.tgz -C /var/www/TgRag data
# хранить 14 дней
find /var/backups/tgrag -name 'rag-*.dump' -mtime +14 -delete
find /var/backups/tgrag -name 'data-*.tgz' -mtime +14 -delete
EOF
sudo chmod +x /var/backups/tgrag/dump.sh
crontab -e   # 0 3 * * * /var/backups/tgrag/dump.sh
```

Восстановление:

```bash
sudo -u postgres pg_restore -d rag --clean --if-exists < /var/backups/tgrag/rag-2026-01-01_0300.dump
tar xzf /var/backups/tgrag/data-2026-01-01_0300.tgz -C /var/www/TgRag
```

Копии складывайте не только на тот же диск: `rclone`/`rsync` на внешнее
хранилище или в S3-совместимое. Проверьте восстановление на тестовой машине
**до** того, как оно понадобится.

## 9. Безопасность

Уже реализовано в проекте (не требует действий): whitelist/код доступа,
изоляция по организации, permission-aware retrieval (🔒 личные документы),
маскирование ПД во всех LLM-вызовах (чат **и** эмбеддинги), Text-to-SQL только
SELECT в read-only транзакции, защита от архивных бомб, точные деньги
(`Decimal`), аудит.

Что нужно сделать на сервере:

1. **Секреты.** `.env` — `chmod 600`, владелец `rag`. Не коммитить
   (`.gitignore` уже исключает). Ключ API давайте отдельный от личного, с
   лимитом расходов в кабинете провайдера.
2. **`STRICT_STARTUP=true`** и непустой `ALLOWED_USER_IDS` **или** свой
   `REG_CODE`. С дефолтным `rag-2026` из README зарегистрируется любой.
3. **Файрвол.** Наружу только SSH. PostgreSQL слушает `127.0.0.1`. Порт
   vLLM/GPU-хоста — в приватной сети.
4. **Права БД.** Пользователь `rag_ro` (только чтение) заведён на шаге 7.3 —
   для Text-to-SQL это второй эшелон защиты помимо read-only транзакции.
5. **`ANONYMIZE_PROMPTS=true`** при любом внешнем endpoint. Стартовая проверка
   в `app/main.py` предупреждает, если выключено, а хост внешний.
6. **systemd-изоляция.** `ProtectSystem=full`, `ProtectHome=read-only`,
   `NoNewPrivileges`, `MemoryMax` — уже в юните из 7.6.
7. **SSH и обновления.** Только ключи, `unattended-upgrades` для security-патчей.
8. **Политика данных.** Зафиксируйте письменно, что именно уходит провайдеру
   (фрагменты документов в промптах) и есть ли у него DPA/резидентность данных в
   нужной юрисдикции. При внешних эмбеддингах — ещё и сырые фрагменты.

## 10. Сколько это стоит

### 10.1. Расход на один вопрос

При включённых по умолчанию настройках экономии (`COMPOSE_MODE=auto`,
`CLASSIFY_WITH_LLM=false`, `RERANKER=crossencoder`):

| Тип вопроса | Вход | Выход | Вызовов API |
|---|---|---|---|
| Факт, сравнение, состав, прогноз, план/факт | 0 | 0 | 0 — ответ собирает код |
| «Что говорится в документах», причины | ~1,6 тыс. | ~250 | 1 (композитор) |
| Ранжирование, гибкий вопрос через SQL | ~1,1 тыс. | ~250 | 1 (композитор) |

Контекст «что говорится о…» — это 5 фрагментов × 200 символов
(`COMPOSER_CONTEXT_ITEMS`/`_CHARS`, настраивается) плюс инструкция композитора и
вопрос. Именно этот блок и определяет цену вопроса.

Если включить «максимум качества» (`COMPOSE_MODE=llm`, `CLASSIFY_WITH_LLM=true`,
`RERANKER=llm`), к каждому вопросу добавляются ещё два вызова:

| Шаг | Вход | Выход |
|---|---|---|
| Классификатор | ~340 | ~40 |
| Реранкер (8 фрагментов × 200 симв.) | ~700 | ~120 |
| Композитор | ~1,6 тыс. | ~250 |
| **Итого** | **~2,6 тыс.** | **~410** |

Загрузка документов: парсинг локальный и токенов не тратит; векторизация тоже
локальная. Токены расходуются только на вопросы и — при `OCR_VLM_ENABLED=true` —
на распознавание сканов.

### 10.2. На сколько хватит 33 ¥ на DeepSeek

Тарифы [DeepSeek](https://api-docs.deepseek.com/zh-cn/quick_start/pricing) в
юанях за 1 млн токенов (актуальны на момент написания; проверяйте страницу):

| | `deepseek-flash` свободно | `deepseek-flash` пик | `deepseek-v4-pro` свободно | `deepseek-v4-pro` пик |
|---|---|---|---|---|
| Вход (кэш-промах) | 1 ¥ | 2 ¥ | 4,5 ¥ | 9 ¥ |
| Вход (кэш-попадание) | 0,02 ¥ | 0,04 ¥ | 0,15 ¥ | 0,30 ¥ |
| Выход | 4 ¥ | 8 ¥ | 13,5 ¥ | 27 ¥ |

Пиковые часы — **будни 9:00–12:00 и 14:00–18:00 по Пекину** (04:00–07:00 и
09:00–13:00 МСК). Всё остальное время, включая все выходные, — свободный тариф
вдвое дешевле. Вечерние вопросы по Москве всегда попадают в свободный тариф.

Расчёт для 33 ¥ на `deepseek-flash` (свободный тариф, без кэша):

| Тип вопроса | Цена вопроса | Хватит на |
|---|---|---|
| «Что говорится в документах» (1,6 тыс. вход + 250 выход) | 0,0026 ¥ | **≈ 12 700 вопросов** |
| Ранжирование / SQL | 0,0021 ¥ | ≈ 15 700 вопросов |
| Факт, сравнение, прогноз | 0 | не тратит баланс вовсе |
| Смешанный поток (модель в 1 вопросе из 4) | 0,00065 ¥ | **≈ 50 000 вопросов** |

В пиковые часы те же цифры делятся примерно на 2 (≈ 7 тыс. и ≈ 29 тыс.), с
10–20% кэша входа — умножаются на 1,05–1,1. На `deepseek-v4-pro`, который в
4,5 раза дороже flash, — делятся примерно на 4,5 (≈ 2,8 тыс. и ≈ 12 тыс.).

Проверить на своей манере спрашивать:

```bash
python -m scripts.balance_forecast                  # таблица выше для 33 ¥
python -m scripts.balance_forecast --model pro
python -m scripts.balance_forecast --peak --cache-hit 0.2
```

Скрипт использует фактический расход из учёта, если API уже вызывался, — тогда
оценка строится на ваших реальных токенах на вопрос, а не на модели расходов.

**Поправка по факту (замер на живом API).** Перечисленные выше цифры — верхняя
граница: они считают весь вход по цене кэш-промаха. На практике провайдер
кэширует повторяющийся префикс промптов, и в прогоне из 7 вопросов **73% входа
пришло по цене кэш-попадания** (0,02 ¥ вместо 1 ¥ за 1 млн — в 50 раз дешевле; в
основном за счёт статической инструкции классификатора). Поэтому оценка по полной
цене даёт примерно вдвое больше реального списания: по факту вышло **0,0017 ¥ на
вопрос** против 0,0035 ¥ «по прайсу». В `/usage` кэш показан отдельной строкой
«Из входа взято из кэша провайдера» — так видно, где экономия уже работает.

Итог: **33 ¥ на `deepseek-flash` — это порядка 12–13 тыс. «содержательных»
вопросов (вывод по документам, ранжирование) или десятки тысяч любых, если
большинство из них — факты и сравнения, которые модель не вызывают вовсе.**

Точные цифры меняются вместе с тарифами провайдера: сверяйтесь с прайсом
([DeepSeek](https://api-docs.deepseek.com/zh-cn/quick_start/pricing),
[OpenAI](https://platform.openai.com/docs/pricing),
[OpenRouter](https://openrouter.ai/models)).

### 10.3. Как срезать расход

- `LLM_MODEL_SMALL` — дешёвая модель на классификацию, реранкинг и SQL: при
  включённых всех шагах это самая крупная экономия.
- `COMPOSE_MODE=auto` — модель не вызывается там, где код уже всё посчитал.
- `RERANKER=crossencoder` или `none` вместо `llm` — минус самый «токеноголодный»
  промпт (фрагменты документов).
- `CLASSIFY_WITH_LLM=false` — правила бесплатны.
- `ANSWER_CACHE_SIZE` — повторные вопросы бесплатны.
- Локальные эмбеддинги — векторизация не тратит токены вовсе.
- Задавайте вопросы по документам в свободные часы DeepSeek (после 13:00 МСК) —
  тариф вдвое ниже при том же качестве.

Заведите лимит расходов в кабинете провайдера: при ошибке API система не
упадёт, а перейдёт на шаблонные ответы.

## 11. Личные расходы из бюджета компании

Руководитель пишет в чат боту:

```
расход: 1500 кофе
расход: кофе 1500              ← порядок суммы и описания любой
расход: 2 500,50 руб — такси   ← копейки и валюта
расход: 300 обед (03.01)       ← дата день.месяц[.год]
доход: 50000 зарплата          ← доходы учитываются отдельно
```

Запись происходит мгновенно и **без вызова LLM** — регулярным разбором, поэтому
не стоит ни токенов, ни времени. Каждая запись попадает в три места:

| Хранилище | Что даёт |
|---|---|
| `ledger_operations` | построчные операции: дата, описание, сумма, категория |
| `facts` (показатель «личные расходы») | факт месяца — поэтому работают вопросы, сравнения и прогноз |
| `data/расходы.xlsx` | журнал: `Дата, Тип, Сумма, Категория, Описание` |

Категория определяется по описанию (`app/categories.py`: Кафе и рестораны,
Транспорт, Продукты…). `/undo` отменяет последнюю запись, пересчитывая месяц.

### Отчёт с колонкой «Личные расходы»

```
/report                                     # в Telegram — файлом
python -m scripts.expenses_report           # на сервере, без Telegram
python -m scripts.expenses_report --list    # только показать записи журнала
```

Файл `Личные_расходы_ГГГГ-ММ.xlsx` содержит два листа:

- **«Отчёт»** — строка на месяц, колонка **«Личные расходы»**, рядом «Личные
  доходы», «Сальдо», «Записей»; ниже — структура расходов по категориям с долями;
- **«По категориям»** — категории по строкам, месяцы по колонкам, итоги.

Важно: отчёт **собирается из базы при каждом запросе** и не дописывается в
загруженный файл компании — оригиналы документов остаются нетронутыми, а цифры
в отчёте всегда соответствуют журналу. Деньги считаются в `Decimal`, поэтому
суммы сходятся копейка в копейку.

### Настройки

```env
EXPENSE_METRIC_NAME=личные расходы    # показатель, в который пишутся расходы
INCOME_METRIC_NAME=личные доходы      # отдельный показатель для доходов
EXPENSE_JOURNAL_FILE=                 # пусто -> {DATA_DIR}/расходы.xlsx
```

Все расходы относятся к организации целиком: бот не различает, кто из
сотрудников внёс запись (в журнале аудита автор фиксируется, в отчёте — нет).

## 13. Диагностика проблем

| Симптом | Причина | Решение |
|---|---|---|
| `[СТОП] LLM API недоступен: LLM API 401` | Неверный ключ | Проверить `LLM_API_KEY`, нет ли лишних кавычек/пробелов |
| `[СТОП] LLM_API_KEY не задан, а LLM_API_BASE указывает на внешний API` | Пустой ключ на внешнем endpoint | Вписать ключ в `.env`; для локального движка (Ollama/vLLM) — любое значение, например `ollama`. Клиент проверяет это до запроса, поэтому невнятного «Illegal header value b'Bearer '» больше не будет |
| В логе `исчерпан баланс (HTTP 402)`, ответы шаблонные | На ключе закончились деньги | Пополнить счёт; система сама вернётся к API (см. [4.6](#46-когда-на-ключе-закончился-баланс)). История: `python -m scripts.llm_usage --balance` |
| Пользователь получил «на ключе закончился баланс» | Штатное предупреждение один раз на эпизод | Ничего делать не нужно — это диагностика, а не ошибка; цифры в ответе верные |
| `LLM API 404` | Неверный `LLM_API_BASE` (нет `/v1` или лишний путь) | База — корень **включая** `/v1`, без `/chat/completions` |
| `LLM API 400 ... max_tokens` | Модель требует `max_completion_tokens` | Уже обрабатывается автоматически; если повторяется — пришлите текст ошибки |
| `LLM API 400 ... temperature` | Модель не принимает нестандартную температуру | Уже обрабатывается: клиент повторяет без `temperature` |
| `LLM API 429` | Рейт-лимит | Клиент повторяет с `Retry-After`; если часто — повысить tier или снизить `ANSWER_RETRIES` |
| В `data/llm_usage.jsonl` записи без токенов, с `event: balance_exhausted` | Фиксируются сбои по деньгам, а не расход | Это ожидаемо, см. `python -m scripts.llm_usage --journal` |
| Ответы всегда шаблонные, в логе `LLM недоступен` | Любая ошибка API | Это by design: данные те же. Смотреть причину в логе |
| `api.telegram.org` недоступен с VPS | Блокировка у провайдера | `TELEGRAM_PROXY=socks5://...` либо другой хостинг |
| Бот молчит, в логе `Conflict: terminated by other getUpdates` | Запущено два экземпляра | Остановить лишний: `systemctl stop rag-bot`, проверить `ps aux \| grep app.main` |
| `relation "documents" does not exist` при работе бота | Таблицы не созданы: `CREATE EXTENSION vector` выполнен не в той базе (например в `postgres`, а не в `rag`), поэтому `create_all` не смог создать таблицы с векторами | Проверить `sudo -u postgres psql -d rag -c "\dx vector"`; выполнить `CREATE EXTENSION IF NOT EXISTS vector;` **в базе `rag`** и перезапустить сервис. Диагностика `check_env.py` покажет и расширение, и список таблиц |
| `relation "vector" does not exist` или ошибки расширения | `CREATE EXTENSION vector` не выполнен в базе `rag` | Выполнить из шага 7.3 под `postgres` в базе `rag` |
| `password authentication failed for user "rag"` | Пароль в `DATABASE_URL` не совпадает с созданным | Сбросить: `ALTER USER rag WITH PASSWORD '...'` |
| Семантический поиск стал хуже после смены модели эмбеддингов | Отпечаток векторов не совпал | `venv/bin/python -m scripts.reindex` |
| Верификатор отклоняет ответы «умной» модели | Модель добавляет посчитанные проценты | Поднять `ANSWER_RETRIES`, либо принять шаблон (`COMPOSE_MODE=auto`) |
| Процесс убит по памяти (`MemoryMax`) | Локальные эмбеддинги + кросс-энкодер в ОЗУ | Поднять `MemoryMax`, либо `RERANKER=heuristic`, либо больше ОЗУ |
| `Отказ запуска: EMBEDDINGS_PROVIDER=api указывает на внешний хост` | Защита от платной векторизации и выноса текстов | Оставить локальные эмбеддинги; осознанное исключение — `REQUIRE_LOCAL_EMBEDDINGS=false` |
| Расход в `/usage` растёт быстрее ожидаемого | Включён дорогой режим или частые повторы верификатора | Проверить `COMPOSE_MODE`, `RERANKER`, `CLASSIFY_WITH_LLM`, `ANSWER_RETRIES`; смотреть разбивку по задачам |
