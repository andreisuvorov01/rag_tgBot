# RAG-ассистент по финансовым отчётам (Telegram)

Реализация **Варианта 2** из [технического описания](описание-проекта-rag-финансы.md):
документы, SQL-база фактов, векторный индекс, эмбеддинги, аналитика и прогнозы —
**локально на своём сервере**; наружу уходит только генерация ответов через **LLM API**
(OpenAI-совместимый или GigaChat).

```
Telegram ──> Бот (aiogram) ──> QA-конвейер ──> Ответ с цитатами
                                 │
        ┌────────────────────────┼──────────────────────────┐
        ▼                        ▼                          ▼
  PostgreSQL/SQLite       Векторный поиск            Аналитика (Python):
  факты, словарь          (pgvector / brute-force)   динамика, тренды,
  показателей, чанки      локальные эмбеддинги       прогноз-ансамбль, бэктест
        │                                                │
        ▼                                                ▼
  Оригиналы файлов              LLM API (единственный внешний сервис):
  (data/uploads)                классификация вопроса, композитор ответа, Text-to-SQL
```

## Что умеет

- Приём файлов в Telegram: **xlsx, xls, csv, pdf, docx, html/htm (веб-выписки), ods (1С/LibreOffice)**, изображения при настроенном OCR,
  до 20 МБ; дедупликация по хэшу; отчёт «что распознано» с подтверждением.
- **Мультestrатегия парсинга PDF** (практика Camelot/Docling/Unstructured): детектированные
  таблицы → если фактов нет, stream-реконструкция колонок по выравниванию текста →
  OCR сканов (Tesseract → опционально vision-LLM). Каждый шаг фиксируется
  в диагностике — всегда видно, почему что-то не извлеклось.
  Отладка любого файла: `python -m scripts.parse_file <файл> [--full]`.
- **Версионирование переизданий**: если новый файл перекрывает периоды прежнего,
  бот предлагает кнопку «🔄 Переиздание вместо…» — старая версия помечается,
  её данные исключаются из анализа (история значений сохраняется в базе), /documents показывает версии.
- Извлечение данных — детальная работа с таблицами:
  - макеты «показатель × период» и вертикальный; чтение xlsx через openpyxl
    с заполнением **объединённых ячеек** (многоярусные шапки, группы над периодами);
  - **план/факт**: колонки «2024 (план)», «факт», «бюджет», «прогноз», «оценка»
    сохраняются с отдельным вариантом; в анализ и прогноз идёт только факт;
  - **разделы и иерархия**: строка-заголовок без чисел становится родительской
    группой, «Итого/Всего» получает имя с префиксом раздела («расходы итого»)
    и связывается с ним, строки «в т.ч. …» — дочерние показатели предыдущей строки;
  - **единицы**: из названия листа, шапки, суффикса строки («Выручка, тыс. руб.»)
    и прямо из ячейки («12,7 млн»);
  - **числа**: бухскобки-минус `(1 200)`, пробельные разделители, европейский
    формат «1.234,56», проценты;
  - **сверка итогов**: сумма строк-детей (из раздела и того же типа показателя)
    против «Итого» — расхождение > 2% даёт предупреждение при загрузке.
- Словарь показателей: точные совпадения → синонимы → семантический поиск;
  дочерние разбивки («… Москва») не склеиваются с родителем; значения,
  отличающиеся от истории на порядки, помечаются для подтверждения человеком.
- Вопросы: точный факт, сравнение периодов, **план/факт (variance)**, **состав показателя (drill-down)**,
  ранжирование по росту, поиск по тексту документов, прогноз; гибкие вопросы —
  через охраняемый Text-to-SQL (только SELECT).
- **Гибридный поиск + реранкинг** (практика Onyx/Anthropic): BM25 + векторы → RRF →
  перез ранжирование (LLM-вариант по умолчанию или локальный кросс-энкодер),
  контекстные аннотации чанков, перекрытие фрагментов; табличные данные
  дополнительно находимы текстом («Показатель «X»: 2023 — 9,80 млн ₽; …»).
- **Агент-верификатор** (grounding, практика FinanceBench): числа в ответе LLM
  сверяются с данными. Допустимые значения берутся из payload и из шаблона,
  с учётом единиц и валюты: `3 500 000` из блока ДАННЫЕ и `3,50 млн ₽` в
  шаблоне — одно и то же число, поэтому корректный ответ не отбрасывается.
  Постороннее число → повтор генерации с замечанием → шаблонный ответ.
  Выдумать цифру в ответе невозможно; оговорка — выдуманное *соотношение*
  (число из данных, приписанное другому показателю) проверкой не ловится.
- **Text-to-SQL под защитой БД**: сгенерированный запрос выполняется в отдельной сессии
  в режиме READ ONLY на уровне PostgreSQL/SQLite — запись невозможна даже при
  ошибке в текстовых фильтрах.
- Прогноз: ансамбль (наивный, средний темп, линейный тренд, сглаживание Хольта,
  сезонный наив), веса по **многоскладочному** бэктестингу (практика Nixtla),
  доверительный интервал, сценарии «что если»
  («если темпы упадут вдвое»), прогноз годовой суммы по месячным данным.
- **Графовая оркестрация агентов** (в духе LangGraph): QA-конвейер — граф
  классификация → резолв → ветвление по намерению → исполнитель → композитор,
  с трассировкой маршрута и защитой от циклов (`app/graph.py`).
- **Permission-aware retrieval** (практика Onyx): документ можно сделать личным
  (🔒 кнопка после загрузки) — его данные исчезают из ответов коллег, RAG-поиска
  и Text-to-SQL; владелец видит всё. Подстановка прав выполняется детерминированно
  (`facts_visible` + `:uid`), LLM не может её обойти.
- **Prompt caching** (провайдер `anthropic`): статический системный промпт и блок
  ДАННЫХ помечены `cache_control` — кэш переиспользуется при повторах верификатора;
  OpenAI/DeepSeek кэшируют статический префикс автоматически.
- **Golden-набор для регрессии** (практика FinanceBench): `python -m scripts.eval_demo`
  — 7 эталонных вопросов по демо-данным, код возврата для CI.
- Ответы: разделение 📊 данные / 🧮 расчёты / 🔮 прогноз / ⚠️ ограничения, цитаты
  до файла-листа-ячейки; если LLM API недоступен — шаблонный ответ на тех же данных.
- **OCR сканов в два эшелона**: локальный Tesseract (по умолчанию, данные не покидают
  сервер), при его отсутствии — опциональный fallback через vision-модель LLM API
  (`OCR_VLM_ENABLED=true`, изображения тогда уходят наружу — режим выключен по умолчанию).

## Быстрый старт (offline-демо, без Telegram и без API)

```bash
pip install -r requirements.txt
python -m scripts.seed_demo     # сгенерирует отчёты 2023–2025, загрузит и задаст вопросы
python -m pytest tests/ -q      # тесты (136)
```

В демо: `LLM_PROVIDER=mock`, эмбеддинги `hash` — полностью без сети.

## Запуск на своём ПК (Windows)

Всё уже подготовлено: `.env` создан, БД — SQLite, зависит только от токена бота.

```bat
:: 1. Токен: @BotFather -> /newbot -> скопируйте в .env:
::    BOT_TOKEN=123456789:AA...
:: 2. Свой Telegram ID у @userinfobot -> в .env:
::    ALLOWED_USER_IDS=123456789
::    (или оставьте пустым и входите кодом REG_CODE=rag-2026)
:: 3. Запуск — двойной клик:
start.bat
```

`start.bat` сначала запускает диагностику (`scripts/check_env.py`: зависимости,
конфиг, БД, эмбеддинги, LLM API, доступность api.telegram.org), затем бота.
Первые шаги в Telegram: `/start` → код (или авто-доступ по whitelist) →
пришлите файл отчёта → задавайте вопросы.

Если `api.telegram.org` недоступен из вашей сети (при этом приложение Telegram
работает — оно ходит на другие серверы Telegram):
- `TELEGRAM_FORCE_IPV4=true` уже включён по умолчанию — помогает при сломанном IPv6;
- впишите прокси вашего VPN-клиента: `TELEGRAM_PROXY=socks5://127.0.0.1:1080`.
Диагностика сама найдёт системный прокси Windows и подскажет его значение.
Без токена и при недоступной сети программа завершится понятной инструкцией,
а не трейсбеком.

### Диск C: заполнен? Виртуальное окружение на D:

Если на C: нет места для torch/sentence-transformers, один раз запустите
`setup_venv.bat`: он создаст `venv` рядом с проектом (на D:), установит туда все
зависимости и перенаправит кэш моделей в `hf-cache` на D:. После этого
`start.bat` автоматически использует `venv\Scripts\python.exe`.
Для включения смыслового поиска раскомментируйте в `.env` блок
`EMBEDDINGS_PROVIDER=sentence_transformers` и при смене модели выполните
`python -m scripts.reindex` (векторы разных моделей несовместимы — система
предупредит об этом при старте).

## Запуск с Telegram (кросс-платформенно)

1. `@BotFather` → создать бота → токен в `BOT_TOKEN`.
2. Узнайте свой Telegram ID (`@userinfobot`) → `ALLOWED_USER_IDS` (или задайте `REG_CODE`).
3. Выберите LLM-провайдера (см. `.env.example`): YandexGPT / OpenRouter / DeepSeek —
   через `LLM_PROVIDER=openai_compatible`, либо GigaChat.
4. Эмбеддинги: `EMBEDDINGS_PROVIDER=sentence_transformers` (локально, ~2 ГБ модель)
   или `hash` на время проверки.
5. Запуск на SQLite:

```bash
copy .env.example .env   # и заполните
python -m app.main
```

## Продакшен: PostgreSQL + pgvector (Docker)

```bash
docker compose up -d --build
```

Поднимается PostgreSQL 16 с расширением pgvector и контейнер бота. В `.env`
`DATABASE_URL` можно не менять — compose передаёт свой. Данные — в volume `pgdata`,
оригиналы файлов — в `appdata`.

## Структура проекта

| Путь | Назначение |
|---|---|
| `app/config.py` | все настройки из `.env` |
| `app/storage.py` | модели SQLAlchemy, pgvector/SQLite-поиск, репозитории |
| `app/embeddings.py` | локальные эмбеддинги: e5/bge (CPU), API, hash-dev |
| `app/llm.py` | клиенты внешнего LLM API + MockLLM (offline) |
| `app/prompts.py` | промпты: классификатор, композитор, Text-to-SQL |
| `app/ingest/` | конвейер документов: парсеры, нормализация, словарь |
| `app/analytics.py` | ряды, статистика, прогнозный ансамбль, бэктестинг |
| `app/qa.py` | маршрутизация запросов, резолв показателей, исполнители |
| `app/security.py` | whitelist/код доступа, обезличивание промптов |
| `app/bot.py` | Telegram-интерфейс (aiogram 3) |
| `scripts/seed_demo.py` | offline-демо end-to-end |

## Безопасность (реализовано)

- Доступ: whitelist Telegram ID и/или код регистрации; изоляция данных по организации.
  При `STRICT_STARTUP=true` (по умолчанию) запуск с дефолтным `REG_CODE` при пустом
  whitelist запрещён — иначе зарегистрироваться смог бы любой, кто знает код из README.
- Оригиналы документов и БД не покидают сервер; в LLM API уходят только промпты.
- `ANONYMIZE_PROMPTS=true`: маскирование выполняется на уровне LLM-клиента
  (`AnonymizingLLM`), поэтому покрыты **все** вызовы — классификатор, Text-to-SQL,
  LLM-реранкер и композитор, а не только промпт ответа. Маскируются ИНН, счета,
  телефоны, e-mail, паспорта и названия организаций (из `ANONYMIZE_ORG_NAMES`
  и из таблицы `organizations`).
- Text-to-SQL: только один SELECT, запрещены DML/DDL, лимит строк; запрос идёт на
  выделенном соединении в режиме только-чтения (снимается до возврата в пул);
  рекомендации: выполнять под пользователем БД с правами только на чтение.
- Защита от архивных «бомб»: перед распаковкой xlsx/docx/ods проверяется суммарный
  размер и число элементов (`MAX_UNCOMPRESSED_MB`, `MAX_ARCHIVE_ENTRIES`), для PDF
  ограничено число страниц (`MAX_PDF_PAGES`).
- Аудит: журнал загрузок и вопросов (`audit_log`).
- HTTPS/TLS — средствами Telegram; для HTTP-эндпоинтов держите порт PostgreSQL
  закрытым извне (compose публикует его только на 127.0.0.1).

## Ограничения текущей версии

- Верификатор проверяет, что каждое число ответа есть в данных, но не проверяет,
  что число приписано правильному показателю или периоду: совпавшее значение из
  другого места таблицы пройдёт проверку.
- Text-to-SQL защищён read-only-транзакцией на уровне БД; для дополнительного
  эшелона можно завести отдельного пользователя PostgreSQL с правами только на чтение
  и указать его в отдельном `DATABASE_URL_RO` (расширение на будущее).
- Многоуровневые «рваные» шапки таблиц PDF могут потребовать ручной сверки
  (система помечает сомнительные значения, а не молча включает их). Проверка
  скачков масштаба работает только при наличии истории по показателю — при первой
  загрузке документа она не срабатывает.
- Денежные значения хранятся как `Float`, а не `Numeric`/`Decimal`: для отчётности
  этого достаточно, но при агрегации возможны расхождения на копейки.
- VLM-OCR по умолчанию выключен: при включении изображения страниц передаются
  внешнему LLM API — включайте, только если это приемлемо по политике конфиденциальности.
